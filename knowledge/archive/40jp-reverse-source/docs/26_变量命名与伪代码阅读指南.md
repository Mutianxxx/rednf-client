# 26 · 变量命名与伪代码阅读指南（回应"变量名都没写"的批评）

> 2026-10-07 有用户反馈：**"根本没啥用，就是 IDA 反编译拿出来，变量名都没写，纯伪代码导出的。"**
> 这个批评对"批量转写层"**部分成立**——本篇讲清楚：哪些成立、我们做了什么改造、
> 改造后的命名规则是什么、以及仍然读不懂时怎么自己验证。
> 配套工具：`tools/semanticize.py`（本轮改造的引擎，可重跑、可校验）。

## 一、批评成立的部分与不成立的部分

| 批评点 | 是否成立 | 事实 |
|---|---|---|
| "就是 IDA 反编译拿出来" | **部分成立** | 批量转写层（T2）的函数体确实是 Hex-Rays 忠实转写——但这是**设计决策**：保留反编译器原始结构 + 原地址，保证可回二进制逐字节对照，不做无据改写 |
| "变量名都没写" | **成立（改造前）** | 改造前全库有 381,012 处 `v1/v2/a1/a2` 式反编译器默认变量名 |
| "纯伪代码导出" | **不成立** | L1 精修层 1,080+ 函数早已逐行精修（见 docs/19）；文件头有模块语义注释、函数有 `// 证:` 证据标注；本轮又完成了全库变量语义化（见下） |

## 二、2026-10-07 全库语义化改造（本轮回应）

`python tools/semanticize.py` 对 src/ 全部 71 个 .cpp 做了三类改造，**全程不改任何逻辑**：

1. **变量语义重命名**：35,530 个变量标识获得语义名（规则见下节）
2. **调用点标注**：2,908 个 `sub_XXXX(` 调用行尾追加了 `// 【语义名】`（该地址在全库有
   语义标签时——来源：函数分隔行注释 2,412 个 + 研究锚点 18 个）
3. **安全性证明**：每个文件通过"骨架校验"（去掉注释/字符串后把标识符全部替换为 `@`，
   前后骨架必须逐字符一致才允许写盘）；`tools/verify_refine.py` 结构级终验：
   **12,172 个函数块结构零改动，9,526 个函数仅标识符/注释级变化**

改造前 → 改造后（示例，来自 `src/game/combat_core.cpp`）：

```c
// 改造前
void **v2; // ecx
v2 = (void **)(this + 4);
*v2 = nullptr;
sub_4015C0((size_t *)v2, szPassword, 0);

// 改造后
void **pThis_4; // ecx
pThis_4 = (void **)(this + 4);
*pThis_4 = nullptr;
sub_4015C0((size_t *)pThis_4, szPassword, 0);  // 【std::string构造赋值】
```

## 三、命名约定速查（读到不认识的变量名时查这里）

所有自动命名的变量名 = **"证据 + 类型/用途"**，前缀即含义：

| 前缀/名字 | 含义 | 例子 |
|---|---|---|
| `pArg1` `pDwArg2` | 指针型参数（pDwArg = 指向 DWORD 的指针） | `void *a1` → `pArg1` |
| `pszArg1` | 字符串参数 | `const char *a1` → `pszArg1` |
| `nArg1` / `uArg1` | 有符号/无符号数值参数 | `int a2` → `nArg2`；`unsigned a2` → `uArg2` |
| `pFn1` | 函数指针参数 | 回调参数 |
| `pFile` | FILE*（来源=fopen 或用法=fclose/fseek 族） | |
| `pMem` | 堆内存（malloc/operator new/HeapAlloc 族） | |
| `pBuf` | 缓冲区（作为 memcpy/memset/fread/qmemcpy 的写入目标） | |
| `psz` | 字符串（作为 strlen/strcmp/strcpy 源 使用） | |
| `pObj` | 对象基址（作为虚表调用的宿主：`(*(int*)pObj + 0x140)(pObj,...)`） | |
| `pThis_4` `pThis_158` | 指向 this+偏移 处的指针（HEX 偏移） | `v2 = (char*)this + 16` → `pThis_10` |
| `fld_158` | 从 this+0x158 处**读出的字段值**（字节偏移，HEX） | `v3 = *(uint32_t*)(this+344)` |
| `fld_e1` | 从 this[1] 读出的字段值（**元素下标**，十进制；this 是 int* 时 =+4 字节） | `v1 = *(this + 1)` |
| `fld_pArg1_78` | 从 pArg1+0x78 读出的字段值 | |
| `pNext` | 链表/指针自追踪（`v4 = (int *)*v4`） | |
| `i` `j` `k` | for 循环下标（仅当初始化是数字字面量） | |
| `nLen` `nCmp` `nVal` `nRead` `dwNow` `nRand` `nPos` | strlen/memcmp/atoi/fread/GetTickCount/rand/ftell 的返回值 | |
| `hCtrl` `hLib` `hDC` `hr` `lRet` | GetDlgItem/LoadLibrary/GetDC/CreateDevice/SendMessage 返回值 | |
| `sub_4D01E0` | **无证据的函数保持原地址名**（铁律：命名有据） | 全库可 grep |

**仍然叫 `v5` 的变量**：所有推断规则都无法给出证据的变量（纯计数器、未知调用返回值、
中间算术结果）。按工程铁律"命名有据"，宁可保留 `v5` 也不编造名字——
这种变量请结合上下文阅读，或用 IDA 打开对应 VA 自行确认后改名。

## 四、三层阅读法（拿到一个函数怎么读）

1. **先看文件头**：每个 cpp 顶部有模块定位注释（哪个系统、来源 dump 区块、研究锚点清单）。
2. **再看函数分隔行**：`// 0x4D71B0 命中主处理器 vt+512` —— 有语义标签的直接告诉你这是啥；
   只有 `sub_XXXX` 的说明该函数还没有语义定名。
3. **读函数体**：
   - 遇到 `pXxx/fld_xxx` → 按上表解名；
   - 遇到 `sub_XXXX(` 行尾 `// 【语义名】` → 直接知道被调函数干什么的；
   - 遇到 `v5` → 结合赋值和比较的上下文读。
4. **存疑时回二进制**：拿函数头的 `// 0x4D71B0` 地址在 IDA（母本
   `DfoVibration_OLD_40JP\work\ida\ARAD_hitstop.i64`）里对照——源码与 Hex-Rays 输出结构逐行对应。

## 五、诚实的局限性声明

1. **自动命名的变量名是规则推断，不是原程序员的命名**。`fld_158` 告诉你"这是 0x158 处
   的字段值"（100% 事实），但不会告诉你"原程序员叫它 m_hp"（无证据，不编）。
2. **覆盖率**：381,012 处反编译器默认变量名中，约 17.9 万处获得了证据化命名
   （35,530 个变量，被引用约 17.9 万次）；其余 20.2 万处是无证据引用，保留原样。
3. **想要更深层精修**（像 L1 那样逐行大白话注释 + 结构体字段全命名）：
   - 路径 A：对某个文件跑人工精修流程（参考 docs/60_子代理重构规范.md）；
   - 路径 B：等 RTTI 类字段还原（docs/22 的长期项）完成后，把 `fld_158` 批量替换为真字段名。
4. **复现/校验命令**：
   ```
   python tools/semanticize.py            # 重建语义化改造（先备份）
   python tools/semanticize.py --verify   # 备份 vs 当前，骨架/行数/VA 复检
   python tools/verify_refine.py          # 结构级终验（12,172 函数块）
   ```
