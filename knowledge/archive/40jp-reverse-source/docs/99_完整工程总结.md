## 第一部分：这个工程是什么

### 1.1 一句话

把 2006 年 DNF（地下城与勇士）**日本版客户端** `ARAD.exe`（3,948,544 字节，2006-06-13 编译，
i386，无壳）的 **12,172 个函数全部反编译重建为可读 C++ 源码**，并做到：
- **每个函数有业务语义头注释**（100%）
- **每个类有字段表**（564 类 / 19,236 字段，带二进制偏移与证据）
- **大部分代码行有白话注释**（有意义行 76.3%）
- **变量名有语义**（游戏类字段真改名 24,652 处 + std/CRT 结构约 3,050 处）

### 1.2 为什么要做

三个用途（docs/25）：
1. **同人开发**：理解了渲染/战斗/AI/协议全链 + 资源格式（NPK/PVF/IMG 已 100% 破译），
   具备制作同人 DNF 的知识基础
2. **协议研究**：106 个包类型 + 91 种发包穷举（docs/24）——客户端侧协议全貌
3. **打击感/机制研究**：继承 40JP 打击感研究 42 轮成果（战斗分发器/命中链/16 时间域/伤害九步公式）

### 1.4 最重要的一条工程铁律

> **命名有据：宁可保留 `v5`/`fld_16C` 也不编造名字。**

这条铁律贯穿全部会话。所以你会看到源码里仍有 50,897 处 `fld_XXX` ——**那不是遗漏，是诚实留白**
（这些位置确实没有证据能确定语义）。同理，占位字段名 `field_XXXX` 也保留而非硬造。

### 3.2 函数卡片流水线（会话 10 建，**省 token 的核心**）

**教训**：会话 9 三个代理消耗 65.8M token 只精修 5 个文件——因为代理反复整块重读
1.2-1.4 万行文件（每个 200+ 次工具调用）。

**方案**：`tools/gen_func_cards.py` 预先把每个函数切成一张 ~12 行卡片
（VA/行区间/签名/字符串证据/被调函数语义名/行数/优先级）：

```bash
python tools/gen_func_cards.py --clean                    # 全库生成卡片
python tools/gen_func_cards.py --batch <文件> 0 90 <输出>  # 生成批量工单
python tools/gen_func_cards.py --stats                    # 看剩余量
```

子代理读 1 张卡（~200 token）+ 按行区间精确 Read 函数体 + 脚本批量 Edit：
**单函数成本 10-45K token**（整文件代理为 100K+），**省约 30 倍**。

### 3.3 字段表还原流水线（会话 11 建）

**原理**：类的每个虚方法都是成员函数（thiscall），其函数体内 `this+N` 访问 = 该类字段访问。
用 `data/class_method_slots.txt`（类→槽位→函数地址）连接 src/ 函数体，即可按类聚合字段。

```bash
python tools/recover_fields.py --all      # 575 类扫描 → data/class_fields/<类>.txt 候选表
python tools/gen_field_struct.py --all    # 候选表 → include/arad/_fields/ struct 骨架
# 再由代理读候选表 + src 证据行 + 同族表 → 覆盖写回语义表
python tools/link_field_tables.py --apply # 549 个类头接入对应字段表
```

### 3.4 std/CRT 结构表（会话 14 建）

MSVC 容器内存布局固定，用「字段访问模式」识别宿主类型：

```bash
python tools/std_container_semantics.py --layout  # 生成 data/std_container_layouts.tsv
python tools/std_container_semantics.py --scan    # 判定 967 个函数的宿主类型
python tools/rename_std_fields.py --apply         # 高置信改名
```

### 3.5 验收体系（三道防线 + 三级判定）

**`python tools/verify_refine.py`**（每轮必跑）：
1. **结构级比对**：函数体「归一」（去注释/字符串占位/标识符→@）后与基线逐行比对——对合法改名不敏感、对结构改动敏感
2. **多版本集合匹配**：同 VA 多文件（L1/L2 双层）归属漂移免疫
3. **三道前置守卫**：
   - **幻影分隔行**：`// 0xNNNNNN` 引用了非函数 VA（会被当函数头拆体）
   - **续行形态**：合法 VA 但后续非「函数名/中文标题/`?` 修饰名」（如 `// 0x569F40 装载…`）
   - **裸注释**：`| +0x` 出现在行内 `//` 之前 = 裸代码（会破坏结构）

**判定**：`PASS` = VA 0 丢失 + 结构 0 改动 + 幻影 0 + 裸注释 0。

**回滚**：`tools/rollback_funcs.py <文件> <VA...>` 按 VA 从快照整体回滚。

### 3.6 子代理纪律（血泪总结）

| 纪律 | 原因 |
|---|---|
| **只加注释/只改标识符，绝不改代码** | 结构完整性是唯一不可破的底线 |
| **脚本批量模式**（收集全部 `(old,new)` 一次性替换） | 38K 行不可能一行一个 Edit |
| **落盘前自查**：裸注释 / 骨架校验 / `^// 0x` 计数 | 三道守卫拦下 90% 事故 |
| **禁止用 grep 做行首扫描** | 本机 grep 是 ugrep，`^// ` 模式**静默失配**——一律用 Python |
| **同一文件绝不并发写** | 会话 12 实测：清洗代理删废话 vs 精修代理加注释互相覆盖 |
| **落笔即走，不返修** | 返修是 token 黑洞（会话 10 有代理 148 次调用做 45 个函数） |
| **同构变体一行带过** | 同族函数（如标量删除器）不重复分析 |

### 3.7 已知踩坑全记录（新会话必读）

1. **`// 0x` 注释行是最危险的坑**（三次事故）：
   - 引用全局变量 `0x8F8520` → 把 0x5AF310 拆空块
   - 引用合法函数 `0x569F40` → 把 0x46F990 拆空块
   - **规则：注释里引用任何地址一律写 `·0x`**（降级记法）
2. **回填注释漏加 `//`**：`return fld_59C; | +0x059C → …`（`|` 成裸代码）——24 行破坏结构
3. **字段名回填时必须区分「声明行」与「语句行」**（两者都要显式加 `//`）
4. **字段值变量 ≠ 临时寄存器变量**：`LOBYTE(x)=…` 复用的变量被误改名（会话 13 回退 38 个）
5. **容器成员 ≠ 局部变量**：`pVecEnd` 可能是「拷贝源指针」而非 vector 成员（会话 14 回退 394 个）
6. **代理的 md5 自证口径不一**：以 `verify_refine.py` 结构级判定为准
7. **shell heredoc 里的反斜杠/反引号会被展开**：写脚本用 Python 文件或 `<<'EOF'` 引号形式
