# 协作与代码提交约定

## 开始前

1. 阅读根目录 `README.md`、`PROJECT-STATUS.md`、本文件和 `project/docs/MODULE-MAP.md`。
2. 从模块地图选一个职责范围。跨模块变更先写清楚数据所有者、调用方向、生命周期和需要的接口，再动代码。
3. 查 `project/docs/REFERENCE-BOUNDARIES.md`。客户端版本事实、40JP 行为参考、推断和未知项必须分开。

## 修改规则

- 以现有 C++17、目录结构和组合式对象为基础。避免按技能 ID 堆分支、复制公共执行器或增加未调用的抽象类。
- `.cpp` 文件唯一归属必须登记到 `project/cmake/source-ownership.json`。修改真实消费者，并增加能区分正确/错误行为的定向测试。
- `simulation` 不得直接依赖 SDL。表现层读状态；SDL、纹理和设备句柄留在 render/backend 边界。
- PVF/PVF 解析和资源读取保留原始字段、顺序、偏移、毫秒、坐标、未知标签、来源路径和身份。未经运行证据验证的跨版本行为用显式策略/适配描述，并写出证据与适用范围。
- 攻击盒、ATK payload、攻击归属、接受命中、纯视觉 ANI、声音事件分开建模。不得由某个视觉资源存在或播放推断伤害。
- 对象状态只由所属模拟对象/服务或明确命令改变。不要新增可任意写 `World` 的辅助接口，不把全部 `World` 交给 UI/表现。
- 每个新实体、状态、异步加载结果、AI 意图和特效都必须定义创建、取消/中断、死亡、换房、恢复时的生命周期。
- 热路径避免逐帧解析 PVF、解压 NPK、复制整个 World/JSON、分配长寿命缓冲或重排稳定数据。无性能数据时先加有界计数或基准，不声称已优化。
- 不提交客户端、PVF/NPK、`ARAD.exe`、用户存档、build/cache、可玩候选、崩溃转储、私有配置或含本机路径的报告。

## 证据分类

每一项新行为在代码注释或相邻文档中标明其证据类型：

- **当前客户端事实**：当前 1031 内容字节和实际运行消费者能共同证明。
- **40JP 结构参考**：反编译源码/二进制提供调用结构；必须说明跨版本映射。
- **推断适配**：工程为支持当前玩法定义的可替换策略，写明依据、适用范围和验证状态。
- **未知/未支持**：缺少足够依据或消费者；保持诊断，不用资源同名匹配假装闭合。

知识库或本机原始资料不是交付包的一部分。团队如获授权访问，应在本机只读挂载，并按来源哈希和版本引用；不要把资料副本直接提交进共享仓库。

## 验证与评审

- 先执行源所有权检查：`python tools/verify_architecture.py --build-dir cache/refactor-build`。它需要该 build 目录已有 `compile_commands.json`；首次配置由 `build.cmd` 完成。
- 运行对应变更路径的测试，再按集成范围运行 `Build-And-Test.cmd`。性能/资源变更需记录同场景、同输入的基线和结果。
- UI/音频/游戏手感的隐藏自动测试不替代真人前台体验。把自动检查、前台测试和原版对照分别标记。
- PR 说明写明：问题与触发方式、改动模块、来源/推断类别、测试命令与结果、剩余风险。保留实际失败日志，不伪报通过。
- 不在用户测试版本运行时覆盖正在执行的 EXE；先完成构建和检查，再生成单独候选。
- 保留平台无关的原始时间、坐标、资源身份、字段顺序和来源关系；Windows/SDL 只是当前平台层。后续 PSP 或其它平台需要原始语义，不能把当前画布缩放、按键替换或资源量化写回来源数据。

## 交接格式

问题反馈至少包括角色/职业、技能或对象、地图、等级/分支、朝向、空放或命中、输入按住状态、分辨率、复现步骤和对应日志/反馈文件。技能或资源错配请给准确显示名称和实际动作，不只给 NPK 文件名。
